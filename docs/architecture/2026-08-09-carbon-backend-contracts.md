# Контракты Carbon backend

## Область

Документ фиксирует контракты `carbon-backend` до Slice 1. Backend — единственный штатный writer уведомлений. `carbon-frontend` и producers работают только через HTTP API backend.

Источник истины — Markdown-файлы в `~/.my-links/logs-obsidian/carbon/Notifications`. PostgreSQL на `127.0.0.1:5433`, database `carbon`, role `carbon` — перестраиваемая рабочая проекция.

## Идентификаторы

- `id`: PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`, только внутренние связи.
- `public_id`: стабильный внешний ID формата `<timestamp-base36>-<source-slug>-<hash-base36-8>`.
- `deduplication_key`: optional producer event key; unique вместе с `source`, когда задан.
- `public_id` и имя Markdown-файла не зависят от PostgreSQL `id`.

`public_id` генерируется после нормализации входных данных. Hash строится из канонического JSON с `source`, `source_event_id`, `occurred_at`, `title`, `body`; алгоритм и fixtures фиксируются в Slice 3. Коллизия не разрешается молча: БД сохраняет уникальность, генератор повторяет попытку с детерминированным nonce.

## Producer API

Базовый путь: `/api/v1`.

### `POST /messages`

Разрешённые поля запроса:

```json
{
  "source": "tg-mon",
  "title": "Вас упомянули в Telegram",
  "occurred_at": "2026-08-09T07:42:18+00:00",
  "source_event_id": "-1001234567890:4815",
  "deduplication_key": "telegram:-1001234567890:4815",
  "body": "Пользователь **Иван** упомянул вас.",
  "tags": ["telegram"]
}
```

Контракт:

- unknown fields отклоняются (`extra=forbid`);
- `source` после нормализации: ASCII lowercase `[a-z0-9-]`, 1–32 символа;
- `title` и `body` обязательны; body — Markdown без raw HTML;
- `occurred_at` timezone-aware, внутри backend приводится к UTC;
- `source_event_id`, `deduplication_key` nullable;
- tags нормализуются, дедуплицируются и имеют ограничение длины;
- `received_at`, `public_id`, `id`, `read_at`, `deleted_at`, `file_path`, `content_hash` задаёт только backend;
- размер запроса и пределы полей задаются конфигурацией;
- новый ресурс возвращается как `201 Created`;
- повторный `(source, deduplication_key)` возвращает существующий ресурс как `200 OK` с заголовком `X-Idempotent-Replay: true` и без нового файла;
- параллельные одинаковые запросы разрешаются уникальным ограничением БД, а не только предварительным SELECT.

### `PATCH /messages/{public_id}`

PATCH нужен для ручной коррекции сообщения из frontend, исправления ошибки producer-а или корректировки metadata. Разрешены только `title`, `body`, `tags`, `occurred_at`.

Нельзя менять `id`, `public_id`, `source`, `source_event_id`, `deduplication_key`, `received_at`, `file_path`, `content_hash`, `read_at` и `deleted_at`. PATCH не является способом переноса файла или ручного управления индексом.

## Error envelope

Все ошибки API, кроме технического сбоя до формирования ответа, используют:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Request validation failed",
    "details": {},
    "request_id": "01J..."
  }
}
```

`code` стабилен и пригоден для frontend; `message` безопасен; `details` не содержит секретов, SQL, stack trace или полного текста сообщения без необходимости; `request_id` попадает в структурированные логи. Минимальные коды: `validation_error`, `authentication_required`, `forbidden`, `not_found`, `conflict`, `payload_too_large`, `storage_error`, `projection_error`, `internal_error`.

## Авторизация

Токены — локальные API-токены Carbon, не LLM-токены. Они нужны producers для POST, viewer для чтения/поиска/SSE и admin для rebuild/reconciliation.

Токены генерируются backend CLI, raw value показывается только при создании, в файле вне Git хранятся hash токена, scope, producer/source и metadata. Файл имеет mode `0600`; raw token не логируется. Каждый producer получает отдельный token. Backend по умолчанию слушает `127.0.0.1`.

## Frontmatter и Markdown

Активный файл: `<vault>/Notifications/YYYY/MM/<public_id>.md`.

Удалённый файл: `<vault>/Notifications/.trash/YYYY/MM/<public_id>.md`.

Канонический frontmatter:

```yaml
schema_version: 1
public_id: td9x8k-tg-mon-3m8v1qa7
source: tg-mon
title: Вас упомянули в Telegram
occurred_at: 2026-08-09T07:42:18Z
received_at: 2026-08-09T07:42:21Z
read_at:
deleted_at:
source_event_id: "-1001234567890:4815"
deduplication_key: "telegram:-1001234567890:4815"
tags:
  - telegram
content_hash: "..."
```

После closing `---` находится исходный `body_markdown`. Порядок полей и сериализация детерминированы; даты всегда UTC в ISO 8601; отсутствующие nullable values сериализуются как YAML null. `search_text` вычисляется из body и не является самостоятельным источником истины.

Запись: temporary file в том же каталоге → write → flush/fsync → atomic `os.replace`. Временные имена имеют отдельный prefix и игнорируются rebuild. Путь строится только из проверенного `public_id`.

## PostgreSQL projection

Минимальные поля `messages`: `id`, `public_id`, `source`, `source_event_id`, `title`, `occurred_at`, `received_at`, `read_at`, `deleted_at`, `deduplication_key`, `tags`, `file_path`, `body_markdown`, `search_text`, `content_hash`, `schema_version`, `search_vector`, `created_at`, `updated_at`. `tags` имеет тип `text[] NOT NULL DEFAULT '{}'` и GIN-индекс: это обеспечивает фильтрацию нормализованных тегов без отдельной реляционной модели в MVP.

`search_vector` обновляется PostgreSQL trigger-ом в той же транзакции, что и row change. Trigger объединяет weighted vectors: title/source — weight A, body — weight B; title/body индексируются русской и английской конфигурациями, source — `simple`. `pg_trgm` используется отдельными GIN-индексами. Embeddings и vector-колонки Carbon MVP не использует, несмотря на наличие pgvector в development image.

## File/DB consistency

Общей транзакции между PostgreSQL и filesystem нет. Реализация обязана явно компенсировать ошибки.

### Create

1. Валидировать и нормализовать request.
2. Начать DB transaction и вставить projection row; unique constraints резервируют deduplication.
3. Записать temporary Markdown, flush/fsync и atomic rename.
4. Commit DB transaction.
5. При ошибке до commit rollback и удалить только файл текущей операции. Невыполненную компенсацию записать для reconciliation.

### Update/read state

1. Взять row lock.
2. Подготовить новый frontmatter/body и temporary file.
3. Atomic replace, сохранив возможность восстановить предыдущую версию.
4. Обновить projection и commit.
5. При ошибке commit восстановить прежний файл и rollback; failure восстановления не скрывать.

### Delete

1. Взять row lock и выставить `deleted_at` в новой frontmatter.
2. Atomic move в `.trash/YYYY/MM`.
3. Обновить projection и commit.
4. При ошибке commit вернуть файл в прежний каталог; reconciliation диагностирует crash между move и commit.

### Rebuild invariants

- rebuild не переписывает корректный исходный Markdown;
- temporary/postоронние файлы игнорируются;
- конфликт одного `public_id` в active и `.trash` не разрешается молча;
- повреждённый файл не прерывает остальные;
- после crash расхождение попадает в отчёт;
- повторный rebuild идемпотентен.

## Pagination, search и SSE

- list API по умолчанию исключает deleted;
- cursor — opaque token с server-side sort key и уникальным tie-breaker;
- сортировка по умолчанию `received_at DESC`, tie-breaker — `public_id`;
- SSE события: `message.created`, `message.updated`, `message.read`, `message.unread`, `message.deleted`;
- SSE имеет heartbeat;
- reconnect не гарантирует replay: frontend выполняет полный refetch;
- SSE не является очередью доставки и не влияет на регистрацию.
