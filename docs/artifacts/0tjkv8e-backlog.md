## `0tjkv9g` — Dependency Injection в backend

### Контекст
Сейчас repository-слой работает с raw `AsyncEngine`: каждый метод сам вызывает `await self._engine.connect()` + ручной `begin()/commit()`. Engine строится в `lifespan` FastAPI и кладётся в `app.state.engine`; handlers достают его через `request.app.state.engine`. Это:
- связывает приложение с FastAPI (DB-доступ невозможен вне request-контекста);
- мешает строгой изоляции тестов (transactional rollback требует, чтобы приложение делило один connection с тестом — см. почему T2 из обсуждения тестов потребует рефакторинга);
- размывает композицию (wiring размазан по `main.py` и handlers).

### Цель
Ввести строгий composition root с DI-контейнером, **независимым от FastAPI**, так чтобы:
- DB-connection (или UoW/session) инжектировался, а не доставался из `app.state`;
- бизнес-логика и repositories не зависели от FastAPI;
- тесты могли подсунуть transaction-bound connection (открывает путь к честному T2 transactional-isolation).

### Кандидаты на инструмент (подтвердить при выполнении)
- **`dependency-injector`** — самый feature-complete DI-контейнер для Python (декларативные контейнеры, wiring, конфигурация). Известен автору; остаётся de-facto для серьёзного DI. Минус — многословность.
- **`lagom`** — лёгкий, type-driven, минималистичный. Хорош для небольших проектов.
- **`injector`** (python-injector) — зрелый, Guice-like.
- Ручной composition root на `typing.Annotated` + тонкая обёртка — для маленького backend может быть достаточно без тяжёлой библиотеки.

### Рекомендация (ориентир)
Для carbon (небольшой backend) — подобрать между `dependency-injector` (если хотим полную мощь) и `lagom`/ручным контейнером (если важна лёгкость). Решение — после короткого сравнительного обзора актуального состояния библиотек на момент выполнения задачи.

### Acceptance
- DB-доступ инжектируется (нет прямого `engine.connect()` в repositories без переданного connection).
- Приложение и repositories тестируемы вне FastAPI.
- Существующие тесты проходят; добавлен тест, демонстрирующий подмену DB-зависимости.

## `0tjkvjh` — Команды запуска backend/frontend

### Контекст
Разработка требует запускать backend (`uv run carbon-backend` из `backend/`) и frontend (`pnpm exec tauri dev` из `frontend/`). Заходить в каталоги неудобно; хочется единый entrypoint вроде `make backend-start` / `frontend-stop` / `all-start`.

### Кандидаты на task runner (подтвердить при выполнении)
- **`just`** (justfile) — современный de-facto для dev-task раннеров в 2026: кросс-платформенный, простой синтаксис (без табов, как у make), Rust-based. Сильный кандидат.
- **`task`** (Taskfile.yml) — YAML-ориентированный, Go-based, популярен, хорошо читается.
- **`Makefile`** — ubiquitous, но с закавыками (таб-чувствительность, плохая диагностика), и его «команды» — не его изначальное предназначение.
- `mise`/`rtx` — тул-менеджер с tasks (избыточно, если нужен только раннер команд).

### Рекомендация (ориентир)
`just` (justfile) как основной вариант — современный, лёгкий, идиоматичный для polyglot-проекта (Python + JS + Rust). Makefile/Task — альтернативы. Решение — при выполнении.

### Acceptance
- Из корня carbon: запуск/стоп backend и frontend, и «всё сразу», одной командой (напр. `just backend-start`, `just all-start`).
- Команды задокументированы в README.
- Не зависит от того, из какого каталога вызвано (корректные cwd).

## `0tjkx14` — Severity (highest/high/medium/low)

### Требования
- Поле `severity` со значениями `highest`, `high`, `medium`, `low` (порядок: highest > high > medium > low). *(Примечание: в исходной формулировке были опечатки «highgest»/«hight» — нормализовано.)*
- Если есть хотя бы одно **непрочитанное** сообщение с `severity > medium` (т.е. `high`/`highest`) — значок tray должен это отражать (отдельное состояние/иконка для «важные непрочитанные»).

### Контекст / охват
Сквозная фича: domain (`ProducerMessage.severity`), vault frontmatter, DB (миграция: колонка `severity`), API (приём/отдача), `carbon-client` (опция `--severity`), frontend (отображение), tray (новое состояние). Значение по умолчанию — `medium` (обратно-совместимо со старыми сообщениями).

### Acceptance
- Сообщения принимаются с `severity`; default `medium`.
- Tray: непрочитанное `high`/`highest` → отдельный значок/состояние.
- Существующие сообщения (без severity) отображаются как `medium`.

## `0tjkwtn` — Табличное представление сообщений

### Требования
- Колонки: дата-время, severity, тема (title), детали (одной строкой — превью тела).
- Severity в ячейке — значком.
- Сортировка всегда от новых к старым.
- Группировка по источнику (source).
- Непрочитанные — жирным шрифтом.

### Кандидаты (исследование)
- **`ag-grid-community` + `ag-grid-vue3`** — мощный, batteries-included (сортировка/группировка/custom cell renderers/row styling из коробки). Минус — тяжёлый bundle, learning curve; Enterprise-фичи платны, но community-версии достаточно.
- **TanStack Table v8** (`@tanstack/vue-table`) — headless, лёгкий, современный; рендеринг свой. Лучше ложится на кастомный layout из `0tjkxay`.
- Ручная таблица на Vue — для малого объёма данных.

### Рекомендация (ориентир)
Сопоставить ag-grid (быстрый старт, но тяжёл) и TanStack Table (легче, headless, лучше вписывается в кастомный layout). Решение — при выполнении, с прицелом на `0tjkxay` (split/docking).

### Acceptance
- Реализованы все колонки, значок severity, сортировка новые→старые, группировка по source, жирный для непрочитанных.

## `0tjkxay` — Layout: таблица сверху, область чтения снизу, разделитель

### Требования
1. Таблица занимает 2/3 по высоте сверху; область чтения — 1/3 снизу.
2. Между ними — **подвижный разделитель**, позволяющий произвольно делить место.
3. Layout напоминает docking — изучить готовые компоненты (не изобретать велосипед).

### Кандидаты (исследование)
- **`splitpanes`** (Vue) — популярный, лёгкий resizable split-panes; закрывает требования (1)+(2).
- `vue3-splitter`, `vue-resizable` — альтернативы split-pane.
- Полноценные docking-библиотеки (Phosphor, DockVue, vue-dock) — избыточны для двух панелей; оправданы только при усложнении layout (много панелей/закладок).

### Рекомендация (ориентир)
Для двух панелей с разделителем достаточно `splitpanes` (или аналога); полноценный docking — overkill, если не планируется рост. Решение — при выполнении.

### Acceptance
- Таблица и область чтения в пропорции 2/3 и 1/3; разделитель перетаскивается; пропорции опционально сохраняются между запусками.

## `0tjkxh0` — Поиск по нескольким словам

### Требования
- Поиск по нескольким словам.
- Изучить возможность применения векторного поиска по содержимому сообщений и теме.

### Контекст
В carbon-backend **уже есть** PostgreSQL FTS (`search_vector`/tsvector) + trigram; endpoint `/messages/search` поддерживает запросы, включая из нескольких слов (tsquery). Значит, мультисловный поиск достижим на текущей FTS — надо уточнить AND/OR-семантику и ранжирование.

### Кандидаты (исследование)
- Текущая FTS (`websearch_to_tsquery`, `ts_rank`) — мультисловный поиск и ранжирование без новых зависимостей.
- **Векторный (семантический) поиск** через `pgvector` + embedding-модель — поиск «по смыслу»; значительно тяжелее (модель, индексация, cost).

### Рекомендация (ориентир)
Сначала доработать мультисловный поиск на FTS (быстрая ценность). Векторный/семантический — отдельным усилением, если потребуется релевантность по смыслу; тогда оценивать `pgvector`. Решение — при выполнении.

### Acceptance
- Поиск по нескольким словам работает (AND/или настраиваемо); ранжирование; решение по векторному поиску зафиксировано.

## `0tjkxlh` — Ссылки на ресурсы в текстах сообщений

### Требования
- Открытие приложений по ссылкам из области просмотра сообщения: «Открыть в Obsidian» (показать сообщение в Obsidian), «Открыть в Telegram» (перейти по ссылке в Telegram) и т.п.
- Формирование ссылок — ответственность отправителя сообщения; со стороны Carbon — обеспечить переход по ссылкам из области просмотра.

### Контекст
В `desktop.ts` уже есть `openExternalUrl` с URI-allowlist (`DEFAULT_ALLOWED_SCHEMES` включает `https:`, `http:`, `tg:`, `obsidian:`; настраивается `VITE_ALLOWED_URI_SCHEMES`). Механизм перехода по `obsidian://`/`tg://` существует. Задача — выделять actionable-ссылки в теле и давать UI «открыть в …».

### Acceptance
- Ссылки в теле кликабельны; внешние схемы проходят через allowlist; глубокие ссылки (`obsidian://`, `tg://`) открывают целевые приложения.

## `0tjkxr5` — Авто-отметка просмотренным

### Требования
1. Если сообщение отображалось в области просмотра **более 1 секунды** — считать его просмотренным, но оставить возможность перевести в непрочитанные.
2. Если сообщение отмечено непрочитанным — поведение (1) для него сохраняется (при повторном показе >1с снова станет прочитанным).

### Контекст
Сейчас отметка — ручная (`POST /read`). Нужен frontend-таймер: при показе сообщения в reading-area стартует таймер; по истечении — `POST /read` (если ещё не read). Сохраняется ручной «mark unread» и цикличность: unread → показ >1с → read → manual unread → снова срабатывает таймер.

### Acceptance
- Показ >1с → авто-read; ручной mark-unread работает и не блокирует повторное авто-read; нет ложных отметок при быстром пролистывании.

## `0tjlcmu` — Пересмотреть аутентификацию для local-only (ВЫПОЛНЕНО)

**Статус:** выполнено (2026-08-11). Реализован вариант (A) — токенная auth убрана целиком, защитой от drive-by стал CORS origin-allowlist. Решение и риск per-source scoping зафиксированы в `docs/decisions/2026-08-11-local-only-auth-removal.md`.

### Контекст (исходный)
Carbon — local-only (bind `127.0.0.1`), но использует per-scope bearer-токены (`producer`/`viewer`/`admin`, хэши в `~/.config/carbon/tokens.json`). Это создаёт операционное трение:
- viewer-токен в `frontend/.env` (нужно генерировать и класть);
- `?token=` для SSE (EventSource не умеет заголовки);
- отдельный токен для каждого consumer-а (`chat-inspector`, `devcats-duty-leave`);
- тестовые токены (я держал producer-токен в `/tmp` — это был временный хак для тестов чата, **не дизайн**).

Для single-user personal app польза от токенов (защита от drive-by браузера / случайного локального доступа) не очевидно окупает это трение.

### Варианты
- **(A) Убрать auth целиком** — только loopback-bind. Трение = 0. Риск: drive-by (DNS-rebinding/CSRF) может писать в canonical vault (инъекция в Obsidian) / читать; для персонального журнала, вероятно, приемлемо. CORS остаётся (webview cross-origin), но без заголовка `Authorization` и `?token=`.
- **(B) Один общий static-секрет** (один токен, один конфиг) вместо per-scope хэшей — меньше трения, но секрет всё ещё в `.env`.
- **(C) Оставить per-scope, но провижионить токены автоматически** при первом запуске `carbon-backend`.

### Рекомендация (ориентир)
Для local-only personal app — **(A)** или **(B)**. Решение — в новом чате, с явной threat-model (drive-by → инъекция в Obsidian vault; чтение заметок).

### Acceptance
- Принято решение по auth; трение минимизировано или обосновано threat-model.
- Если auth убран — обновить DR `2026-08-11-cors-and-sse-auth.md` и код (убрать `Authorization`/`?token=`, `viewer_principal`), обновить тесты и `carbon-client` (опциональный токен).
